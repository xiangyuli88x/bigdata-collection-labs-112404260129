# 实验二答辩速查 · 批量入库核对优化

打开 [storage.py 的 insert_batch()](storage.py#L213)，在 VS Code 中搜索 `after_records`，就能找到写入后核对的代码。它位于 `connection.commit()` 上方。

## 新旧代码对照

旧版每核对一条房源，都会重新遍历 `after`，生成内容相同的集合。

```python
if any(record not in {row[1:] for row in after} for record in records):
    raise StorageError("事务内8字段核对失败，撤销本次事务")
```

新版先从写入后的快照建一次集合，再在同一个集合里查本批的每条房源。

```python
after_records = {row[1:] for row in after}
if any(record not in after_records for record in records):
    raise StorageError("事务内8字段核对失败，撤销本次事务")
```

| 对比项 | 旧版 | 新版 |
| --- | ---: | ---: |
| 写入后 500 条，本批核对 500 条，全部通过时建集合的次数 | 500 次 | 1 次 |
| 建集合时遍历的记录量 | 250,000 条次 | 500 条次 |
| 集合查找次数 | 500 次 | 500 次 |

写入后的表有 `n` 条，本批要核对 `m` 条。按集合操作的平均开销计算，这段核对从约 `O(n × m)` 降到 `O(n + m)`。表中的条次是工作量示例，实际入库还包含 SQL 执行、读取快照和提交事务的耗时。

## 答辩时怎么讲

- **怎么防重复？** 写入前，把已有记录的 8 个字段存入集合 `existing`。遇到缺失房源就加入 `missing`，同时加入 `existing`。这样库里已有的记录和本批内部重复的记录都会跳过。
- **改的是哪一步？** 写入后的完整快照 `after` 已经读到了 Python。旧版每查一条就重建集合，新版把这份集合提前建好，整个循环共用。
- **为什么核对结果一样？** 两种写法都用 `row[1:]` 跳过 `id`，逐条比较 8 个字段。条数核对、原记录核对以及提交和回滚仍在同一事务流程中。

## 验证结果

- 现有 18 项单元测试通过。额外检查了重复记录只插入一次，以及回读字段不一致时触发回滚。
- MySQL 会话临时表验证了提交、回滚和 8 个字段的一致性，独立的第二次批量调用新增 0 条。真实 `houseinfo` 表在检查前后均为 498 条。
